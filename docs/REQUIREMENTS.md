# 장바구니 주문/쿠폰 요구사항

## 목표

장바구니 주문/쿠폰 흐름에서는 쿠폰, 배송비, 주문 확인, 주문 생성 흐름을 해석하고 FE-BE 책임 경계를 설계한다. 결제 금액에 영향을 주는 핵심 데이터와 계산 결과는 클라이언트가 임의로 확정하지 않고, 서버가 관리하는 장바구니/상품/쿠폰 데이터를 기준으로 계산하고 검증한다.

## 설계 원칙

- 프론트엔드는 금액 계산 로직을 갖지 않는다.
- 서버에 결제 금액 미리보기 API를 두고, 프론트엔드는 서버가 계산한 금액만 화면에 표시한다.
- 프론트엔드는 쿠폰 체크/해제 또는 제주도 및 도서산간 지역 여부 변경 시 현재 선택 상태로 결제 금액 미리보기 API를 호출한다.
- "총 n원 할인 쿠폰 사용하기"의 `n원`은 프론트엔드가 계산하지 않고, 서버의 결제 금액 미리보기 응답을 기준으로 표시한다.
- 제주도 및 도서산간 지역 체크 여부는 주문 생성 전까지 DB에 저장하지 않고, 결제 금액 미리보기 요청의 계산 입력값으로만 사용한다.
- 서버는 결제 금액 미리보기 요청이 성공하면 서버가 실제 적용한 쿠폰 ID 목록과 배송 조건을 PreorderStore에 반영한다.
- 주문 생성 시 프론트엔드는 `preorderId`와 최종 결제 금액 `expectedTotalPaymentAmount`만 보내 사용자가 동의한 금액과 서버 재계산 금액이 같은지 확인한다.
- 서버는 주문 생성 시점에 preorder, PreorderStore의 적용 쿠폰/배송 조건, 쿠폰 정책, 서버 시간을 기준으로 결제 금액을 반드시 다시 계산한다.
- preorder는 DB 접근을 줄이기 위한 캐시가 아니라, 장바구니와 확정 주문 사이에서 사용하는 짧은 생명주기의 주문 세션으로 정의한다.
- PreorderStore는 이번 단계에서 서버 인메모리 Map 기반 TTL 저장소로 구현한다.
- 서버 인메모리 PreorderStore는 서버 재시작 시 데이터가 사라질 수 있으며, 만료되거나 사라진 preorder는 주문 확인 흐름을 다시 시작하도록 처리한다.

## 상태별 SSOT

`Server`는 요청 시점에 값을 계산하고 검증하는 책임 주체를 의미한다. 반면 `Server In-Memory Cache`는 서버 프로세스 메모리에 TTL로 보관되는 휘발성 저장소를 의미한다.

| 상태 | SSOT | 설명 |
| --- | --- | --- |
| 상품 정보 | DB | 상품명, 가격, 썸네일, 재고의 원천이다. preorder 생성 시 서버가 DB에서 조회한다. |
| 장바구니 항목 | DB | 장바구니 상품과 수량의 원천이다. 주문 확인 시작 시 선택된 cart ID를 서버가 검증한다. |
| 쿠폰 정책 | DB | 쿠폰 조건, 혜택, 만료일의 원천이다. 서버 시간과 preorder를 기준으로 사용 가능 여부와 적용 결과를 계산한다. |
| 확정 주문 | DB | 주문 생성 성공 후 저장되는 최종 주문 데이터의 원천이다. |
| preorder | Server In-Memory Cache | 장바구니와 확정 주문 사이의 짧은 생명주기 주문 세션이다. 서버 메모리의 Map 기반 TTL 저장소에 저장하며, 주문 확인, 쿠폰 조회, 결제 금액 미리보기, 주문 생성의 기준 데이터다. |
| 적용된 쿠폰 ID | Server In-Memory Cache | 결제 금액 미리보기 요청에서 서버가 실제 적용한 쿠폰 ID 목록이다. 주문 생성 시 서버가 이 값을 기준으로 다시 검증하고 계산한다. |
| 적용된 배송 조건 | Server In-Memory Cache | 결제 금액 미리보기 요청에 반영된 배송 조건이다. 주문 생성 시 서버가 이 값을 기준으로 배송비를 다시 계산한다. |
| 추천 쿠폰 ID | Server | preorder와 배송 조건을 기준으로 서버가 계산한 최대 할인 쿠폰 조합이다. 프론트엔드는 쿠폰 모달을 처음 열 때 선택값이 비어 있으면 이 값을 초기 선택값으로 사용한다. |
| 결제 금액 미리보기 결과 | Server | 주문 금액, 상품 할인 금액, 배송비 할인 금액, 총 할인 금액, 배송비, 최종 결제 금액의 화면 표시 원천이다. 프론트엔드는 서버 계산 결과를 복사해 보여줄 뿐 직접 계산하지 않는다. |
| 최종 주문 금액 | Server | 주문 생성 시점에 preorder, 적용 쿠폰, 배송 조건, 쿠폰 정책, 서버 시간을 기준으로 서버가 재계산한 값이다. 주문 생성 성공 후에는 확정 주문 데이터로 DB에 저장된다. |
| 장바구니 선택 여부 | Frontend | 사용자가 현재 장바구니에서 어떤 항목을 주문할지 고르는 화면 상태다. 서버에는 주문 확인 시작 시 선택된 cart ID 목록만 전달한다. |
| 선택 중인 쿠폰 ID | Frontend | 사용자가 체크 중인 임시 UI 상태다. 변경 시 결제 금액 미리보기 요청의 `couponIds`로 서버에 전달한다. |
| 선택 중인 배송 조건 | Frontend | 제주도 및 도서산간 지역 체크 여부를 포함한 임시 UI 상태다. DB에는 저장하지 않고, 변경 시 결제 금액 미리보기 요청의 `isRemoteArea`로 서버에 전달한다. |
| 사용자가 확인한 결제 금액 스냅샷 | Frontend | 프론트엔드가 마지막 결제 금액 미리보기 응답의 주문 금액, 상품 할인 금액, 배송비 할인 금액, 총 할인 금액, 배송비, 최종 결제 금액을 화면 표시용으로 보관한 값이다. 서버 신뢰값이 아니라 사용자가 본 금액을 보존하기 위한 UX 검증용 스냅샷이며, 주문 생성 요청에는 이 중 `expectedTotalPaymentAmount`만 전송한다. |

## 기능 요구사항

### 1. 주문 세션 및 임시 주문서

- [x] 장바구니에서 사용자가 주문할 상품을 선택하고 [주문확인] 버튼을 클릭할 수 있다.
- [x] 프론트엔드는 선택된 장바구니 항목 ID 목록만 서버에 전송한다.
- [x] 서버는 전달받은 장바구니 항목 ID를 검증한다.
- [x] 서버는 DB에서 장바구니 항목의 `productId`, `quantity`를 조회한다.
- [x] 서버는 DB에서 최신 상품 정보인 상품명, 가격, 썸네일을 조회한다.
- [x] 서버는 조회한 주문 대상 상품 정보를 임시 주문 데이터인 preorder로 저장하고 `preorderId`를 발급한다.
- [x] preorder는 장바구니에서 선택된 항목을 기준으로 생성되는 주문 세션이다.
- [x] preorder는 주문 확인, 쿠폰 조회, 결제 금액 미리보기, 주문 생성 API가 공유하는 기준 데이터로 사용한다.
- [x] PreorderStore는 서버 인메모리 Map으로 구현한다.
- [x] preorder는 짧은 TTL을 가지며, TTL이 만료되면 주문 확인 흐름을 다시 시작해야 한다.
- [x] PreorderStore는 preorder 저장 시 만료 시각을 함께 저장한다.
- [x] PreorderStore는 preorder 조회 시 만료 여부를 검사하고, 만료된 preorder는 삭제한 뒤 없는 데이터처럼 처리한다.
- [x] preorder는 주문 생성 성공 시 한 번만 소비된다.
- [x] 주문 생성 성공 시 PreorderStore에서 해당 preorder를 삭제한다.
- [x] 서버 재시작으로 인메모리 preorder가 사라진 경우에도 만료와 같은 복구 흐름으로 처리한다.
- [x] preorder의 가격 원천은 주문 확인 시점에 서버가 DB에서 조회한 상품 가격이다.
- [x] 주문 생성 시점에는 preorder 상품 정보와 서버의 쿠폰/배송 정책을 기준으로 금액을 다시 계산한다.
- [x] 주문 확인 페이지는 `preorderId`를 기준으로 서버에 preorder 정보를 요청해 주문 대상 상품을 렌더링한다.
- [x] 주문 확인 페이지는 기본 조건인 쿠폰 없음, 제주도 및 도서산간 지역 아님으로 결제 금액 미리보기를 요청해 최초 결제 금액을 표시한다.
- [x] `preorderId`가 없거나 만료된 경우 사용자가 주문 확인 흐름을 다시 시작할 수 있도록 안내한다.

### 2. 상태 설계

- [x] 상품 정보, 수량, 선택 여부, 쿠폰, 배송지 추가 배송 여부는 하나의 원천 상태를 기준으로 해석한다.
- [x] 서버는 상품 정보, 장바구니 항목, 쿠폰 정책, 임시 주문서, 확정 주문의 원천 상태를 관리한다.
- [x] 프론트엔드는 사용자의 화면 상호작용 상태를 관리한다.
- [x] 프론트엔드가 관리하는 상태는 상품 선택 여부, 선택 중인 쿠폰 ID, 제주도 및 도서산간 지역 체크 여부, 결제 금액 미리보기 응답의 화면 표시용 복사본, 로딩/에러 상태로 제한한다.
- [x] 주문 금액, 상품 할인 금액, 배송비 할인 금액, 총 할인 금액, 배송비, 최종 결제 금액 계산은 서버가 전담한다.
- [x] 프론트엔드는 서버가 계산한 결제 금액 미리보기 응답을 화면에 표시한다.
- [x] 프론트엔드는 쿠폰/배송비/최종 결제 금액을 직접 계산하지 않는다.
- [x] 프론트엔드는 제주도 및 도서산간 지역 체크 여부를 주문 생성 전까지 서버에 저장하지 않는다.
- [x] 프론트엔드가 보관하는 결제 금액 미리보기 응답은 사용자가 본 금액 스냅샷이며, 서버는 이 값을 신뢰하지 않고 재계산한다.
- [x] 프론트엔드가 주문 요청 시 전달하는 `expectedTotalPaymentAmount`는 사용자가 동의한 최종 결제 금액 확인용이며, 결제 금액 스냅샷 중 최종 결제 금액만 전송한 값이다.

### 3. 쿠폰 도메인

쿠폰 데이터는 등록, 수정, 삭제 API 없이 DB에 하드코딩된 데이터로 관리한다.

- [x] 사용 가능한 쿠폰 목록을 조회할 수 있다.
- [x] 서버는 `preorderId`에 저장된 주문 상품과 서버 시간을 기준으로 각 쿠폰의 사용 가능 여부를 계산한다.
- [x] 서버는 쿠폰 목록 응답에 사용 가능 여부 또는 비활성화 사유를 포함한다.
- [x] 서버는 쿠폰 목록 응답에 현재 preorder와 배송 조건 기준의 최대 할인 추천 쿠폰 ID 목록을 포함한다.
- [x] 프론트엔드는 쿠폰 모달을 처음 열 때 선택된 쿠폰이 없으면 서버가 내려준 추천 쿠폰 ID 목록을 자동 선택한다.
- [x] 프론트엔드는 사용자가 최대 2개의 쿠폰만 선택할 수 있는 UI를 제공한다.
- [x] 프론트엔드는 쿠폰을 체크하거나 해제할 때 현재 선택 중인 쿠폰 ID 목록으로 결제 금액 미리보기를 요청한다.
- [x] 서버는 결제 금액 미리보기 요청에서 실제 적용된 쿠폰 ID 목록을 PreorderStore에 저장한다.
- [x] 쿠폰 적용 버튼의 `n원` 표시는 결제 금액 미리보기 응답의 쿠폰 할인 합계 금액을 기준으로 한다.
- [x] 무료 배송 쿠폰이 기본 배송비와 도서산간 추가 배송비를 모두 무료 처리하면 쿠폰 적용 버튼의 `n원`에 해당 배송비 할인액을 포함한다.
- [x] 쿠폰 응답은 최상위 `type`을 사용하지 않고, `code`로 쿠폰 정책을 식별한다.
- [x] 쿠폰 조건과 혜택은 `target`, `rule`, `params` 구조로 표현하고, 서버는 `target`과 `rule`을 기준으로 해석한다.
- [x] 상품 할인 쿠폰의 적용 순서는 `benefit.discountType`으로 구분하며, `FIXED`를 먼저 적용한 뒤 `RATE`를 적용한다.

#### 쿠폰 정책

| 코드 | 이름 | 조건 | 혜택 | 만료일 |
| --- | --- | --- | --- | --- |
| `FIXED5000` | 5,000원 할인 쿠폰 | 주문 금액 100,000원 이상 | 5,000원 할인 | 2026-11-30 |
| `BOGO` | 2+1 쿠폰 | 동일 상품 2개 이상 구매 | 적용 가능 상품 중 단가가 가장 높은 상품 1개를 무료 증정하고, 해당 상품 1개 정가를 주문 금액과 상품 할인 금액에 함께 반영 | 2026-06-30 |
| `FREESHIPPING` | 무료 배송 쿠폰 | 주문 금액 50,000원 이상 | 기본 배송비와 도서산간 추가 배송비 무료 | 2026-08-31 |
| `MIRACLESALE` | 30% 시간제 할인 쿠폰 | 오전 4시 이상 오전 7시 미만 | 정액성 할인 적용 후 남은 상품 금액의 30% 할인 | 2026-07-31 |

### 4. 쿠폰 복합 적용

- [x] 최대 2개의 쿠폰을 동시에 적용할 수 있다.
- [x] 서버는 요청된 쿠폰이 존재하는지, 만료되지 않았는지, 현재 주문에 적용 가능한지 검증한다.
- [x] 적용 가능한 쿠폰 조합이 여러 개인 경우 서버는 총 할인 효과가 가장 큰 조합을 선택한다.
- [x] 정액성 쿠폰인 `FIXED5000`, `BOGO`를 먼저 적용한다.
- [x] 정율 쿠폰인 `MIRACLESALE`은 정액성 할인이 적용된 상품 금액을 기준으로 적용한다.
- [x] `BOGO`는 무료 증정 상품의 정가를 주문 금액에 포함하고, 같은 금액을 상품 할인 금액으로 차감한다.
- [x] `FREESHIPPING`은 상품 할인 금액이 아니라 배송비 할인으로 계산한다.
- [x] 서버는 결제 금액 미리보기 응답에 적용된 쿠폰, 제외된 쿠폰, 제외 사유를 포함한다.

### 5. 배송비 정책

- [x] 배송비 계산 기준 주문 금액은 쿠폰 적용 전 상품 금액이다.
- [x] 쿠폰 적용 전 주문 금액이 100,000원 이상이면 기본 배송비는 무료다.
- [x] 쿠폰 적용 전 주문 금액이 100,000원 미만이면 기본 배송비 3,000원을 부과한다.
- [x] 제주도 및 도서산간 지역을 선택하면 추가 배송비 3,000원을 부과한다.
- [x] `FREESHIPPING` 쿠폰이 적용되면 기본 배송비와 도서산간 추가 배송비를 모두 무료 처리한다.
- [x] 프론트엔드는 "제주도 및 도서산간 지역" 체크박스를 제공한다.
- [x] 제주도 및 도서산간 지역 체크 여부는 결제 금액 미리보기 요청의 계산 입력값으로만 사용한다.
- [x] 제주도 및 도서산간 지역 체크 여부는 주문 생성 성공 전까지 DB에 저장하지 않는다.

### 6. 주문 생성 및 무결성 검증

- [x] 사용자가 쿠폰을 체크하거나 해제하면 프론트엔드는 현재 `preorderId`, `couponIds`, `isRemoteArea`로 결제 금액 미리보기를 요청한다.
- [x] 사용자가 제주도 및 도서산간 지역 여부를 변경하면 프론트엔드는 DB를 업데이트하지 않고, 현재 `preorderId`, `couponIds`, `isRemoteArea`로 결제 금액 미리보기를 요청한다.
- [x] 서버는 preorder, 요청의 쿠폰/배송 조건, 쿠폰 정책, 서버 시간을 기준으로 주문 금액, 상품 할인 금액, 배송비 할인 금액, 총 할인 금액, 배송비, 최종 결제 금액을 계산해 응답한다.
- [x] 서버는 결제 금액 미리보기 요청이 성공하면 실제 적용된 쿠폰 ID 목록과 배송 조건을 PreorderStore에 저장한다.
- [x] 사용자가 [결제하기] 버튼을 클릭하면 프론트엔드는 `preorderId`와 화면에 표시된 `expectedTotalPaymentAmount`를 서버에 전송한다.
- [x] 서버는 `preorderId`로 임시 주문 데이터를 조회한다.
- [x] 서버는 DB의 쿠폰 데이터와 서버 시간을 기준으로 쿠폰 유효성을 다시 검증한다.
- [x] 서버는 PreorderStore에 저장된 적용 쿠폰 ID 목록과 배송 조건을 기준으로 상품 금액, 상품 할인 금액, 배송비 할인 금액, 총 할인 금액, 배송비, 최종 결제 금액을 자체 재계산한다.
- [x] 서버는 프론트엔드가 보낸 `expectedTotalPaymentAmount`와 서버 재계산 최종 결제 금액이 일치하는지 비교한다.
- [x] 금액이 일치하지 않거나 쿠폰이 유효하지 않으면 주문 생성을 거절한다.
- [x] 주문 생성 성공 시 서버는 주문 테이블에 확정 주문을 저장한다.
- [x] 상품 재고 또는 총수량 차감은 현재 미션 범위 밖으로 두고 구현하지 않는다.
- [x] 주문 생성 성공 시 서버는 선택된 장바구니 항목을 삭제한다.
- [x] 주문 생성 성공 시 서버는 `orderId`를 응답한다.
- [x] 프론트엔드는 주문 생성 실패 시 쿠폰 목록과 주문 금액을 최신화하거나 사용자에게 복구 가능한 오류를 안내한다.

### 7. 결제 금액 확인

- [x] 결제 API는 구현하지 않는다.
- [x] 주문 생성 후 프론트엔드는 `orderId`를 기준으로 주문 요약 정보를 조회한다.
- [x] 서버는 주문 ID를 기준으로 주문 상품 종류 수, 총 수량, 총 결제 금액을 응답한다.
- [x] 주문 ID가 유효하지 않으면 프론트엔드는 재조회 또는 오류 안내 UI를 제공한다.
