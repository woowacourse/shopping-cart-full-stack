# 장바구니 3단계 요구사항

## 목표

장바구니 3단계에서는 기능 구현에 앞서 쿠폰, 배송비, 주문 확인 흐름을 해석하고 FE-BE 책임 경계를 설계한다. 결제 금액에 영향을 주는 핵심 데이터와 계산 결과는 클라이언트가 임의로 확정하지 않고, 서버가 관리하는 장바구니/상품/쿠폰 데이터를 기준으로 검증한다.


## 기능 요구사항

### 1. 주문 세션 및 임시 주문서

- [ ] 장바구니에서 사용자가 주문할 상품을 선택하고 [주문확인] 버튼을 클릭할 수 있다.
- [ ] 프론트엔드는 선택된 장바구니 항목 ID 목록만 서버에 전송한다.
- [ ] 서버는 전달받은 장바구니 항목 ID를 검증한다.
- [ ] 서버는 DB에서 장바구니 항목의 `productId`, `quantity`를 조회한다.
- [ ] 서버는 DB에서 최신 상품 정보인 상품명, 가격, 썸네일, 재고를 조회한다.
- [ ] 서버는 조회한 주문 대상 상품 정보를 임시 주문 데이터인 preorder로 저장하고 `preorderId`를 발급한다.
- [ ] 주문 확인 페이지는 `preorderId`를 기준으로 서버에 preorder 정보를 요청해 주문 대상 상품을 렌더링한다.
- [ ] `preorderId`가 없거나 만료된 경우 사용자가 주문 확인 흐름을 다시 시작할 수 있도록 안내한다.

### 2. 상태 설계

- [ ] 상품 정보, 수량, 선택 여부, 쿠폰, 배송지 추가 배송 여부는 하나의 원천 상태를 기준으로 해석한다.
- [ ] 서버는 상품 정보, 장바구니 항목, 쿠폰 정책, 임시 주문서, 확정 주문의 원천 상태를 관리한다.
- [ ] 프론트엔드는 사용자의 화면 상호작용 상태를 관리한다.
- [ ] 프론트엔드가 관리하는 상태는 상품 선택 여부, 선택한 쿠폰 ID, 제주도 및 도서산간 지역 체크 여부, 로딩/에러 상태로 제한한다.
- [ ] 주문 금액, 할인 금액, 배송비, 최종 결제 금액의 최종 판단은 서버 계산 결과를 기준으로 한다.
- [ ] 프론트엔드가 화면 표시나 요청 검증을 위해 예상 금액을 보관하더라도 서버는 그 값을 신뢰하지 않고 재계산한다.

### 3. 쿠폰 도메인

쿠폰 데이터는 등록, 수정, 삭제 API 없이 DB에 하드코딩된 데이터로 관리한다.

- [ ] 사용 가능한 쿠폰 목록을 조회할 수 있다.
- [ ] 서버는 `preorderId`에 저장된 주문 상품과 서버 시간을 기준으로 각 쿠폰의 사용 가능 여부를 계산한다.
- [ ] 서버는 쿠폰 목록 응답에 사용 가능 여부 또는 비활성화 사유를 포함한다.
- [ ] 프론트엔드는 사용자가 최대 2개의 쿠폰만 선택할 수 있는 UI를 제공한다.

#### 쿠폰 정책

| 코드 | 이름 | 조건 | 혜택 | 만료일 |
| --- | --- | --- | --- | --- |
| `FIXED5000` | 5,000원 할인 쿠폰 | 주문 금액 100,000원 이상 | 5,000원 할인 | 2026-11-30 |
| `BOGO` | 2+1 쿠폰 | 동일 상품 2개 이상 구매 | 적용 가능 상품 중 단가가 가장 높은 상품 1개 금액 할인 | 2026-06-30 |
| `FREESHIPPING` | 무료 배송 쿠폰 | 주문 금액 50,000원 이상 | 기본 배송비와 도서산간 추가 배송비 무료 | 2026-08-31 |
| `MIRACLESALE` | 30% 시간제 할인 쿠폰 | 오전 4시 이상 오전 7시 미만 | 정액성 할인 적용 후 남은 상품 금액의 30% 할인 | 2026-07-31 |

### 4. 쿠폰 복합 적용

- [ ] 최대 2개의 쿠폰을 동시에 적용할 수 있다.
- [ ] 서버는 요청된 쿠폰이 존재하는지, 만료되지 않았는지, 현재 주문에 적용 가능한지 검증한다.
- [ ] 적용 가능한 쿠폰 조합이 여러 개인 경우 서버는 총 할인 효과가 가장 큰 조합을 선택한다.
- [ ] 정액성 쿠폰인 `FIXED5000`, `BOGO`를 먼저 적용한다.
- [ ] 정율 쿠폰인 `MIRACLESALE`은 정액성 할인이 적용된 상품 금액을 기준으로 적용한다.
- [ ] `FREESHIPPING`은 상품 할인 금액이 아니라 배송비 할인으로 계산한다.
- [ ] 서버는 적용된 쿠폰, 제외된 쿠폰, 제외 사유를 응답에 포함할 수 있다.

### 5. 배송비 정책

- [ ] 배송비 계산 기준 주문 금액은 쿠폰 적용 전 상품 금액이다.
- [ ] 쿠폰 적용 전 주문 금액이 100,000원 이상이면 기본 배송비는 무료다.
- [ ] 쿠폰 적용 전 주문 금액이 100,000원 미만이면 기본 배송비 3,000원을 부과한다.
- [ ] 제주도 및 도서산간 지역을 선택하면 추가 배송비 3,000원을 부과한다.
- [ ] `FREESHIPPING` 쿠폰이 적용되면 기본 배송비와 도서산간 추가 배송비를 모두 무료 처리한다.
- [ ] 프론트엔드는 "제주도 및 도서산간 지역" 체크박스를 제공한다.

### 6. 주문 생성 및 무결성 검증

- [ ] 사용자가 [결제하기] 버튼을 클릭하면 프론트엔드는 `preorderId`, 선택한 `couponIds`, `isRemoteArea`, 화면에 표시한 예상 금액을 서버에 전송한다.
- [ ] 서버는 `preorderId`로 임시 주문 데이터를 조회한다.
- [ ] 서버는 DB의 쿠폰 데이터와 서버 시간을 기준으로 쿠폰 유효성을 다시 검증한다.
- [ ] 서버는 상품 금액, 할인 금액, 배송비, 최종 결제 금액을 자체 재계산한다.
- [ ] 서버는 프론트엔드가 보낸 예상 금액과 서버 재계산 금액이 일치하는지 비교한다.
- [ ] 금액이 일치하지 않거나 쿠폰이 유효하지 않으면 주문 생성을 거절한다.
- [ ] 주문 생성 성공 시 서버는 주문 테이블에 확정 주문을 저장한다.
- [ ] 주문 생성 성공 시 서버는 상품 재고 또는 총수량을 차감한다.
- [ ] 주문 생성 성공 시 서버는 선택된 장바구니 항목을 삭제한다.
- [ ] 주문 생성 성공 시 서버는 `orderId`를 응답한다.
- [ ] 프론트엔드는 주문 생성 실패 시 쿠폰 목록과 주문 금액을 최신화하거나 사용자에게 복구 가능한 오류를 안내한다.

### 7. 결제 금액 확인

- [ ] 결제 API는 구현하지 않는다.
- [ ] 주문 생성 후 프론트엔드는 `orderId`를 기준으로 주문 요약 정보를 조회한다.
- [ ] 서버는 주문 ID를 기준으로 주문 상품 종류 수, 총 수량, 총 결제 금액을 응답한다.
- [ ] 주문 ID가 유효하지 않으면 프론트엔드는 재조회 또는 오류 안내 UI를 제공한다.

## API 설계 요구사항

- [ ] 쿠폰 목록 조회 API를 설계한다.
- [ ] 임시 주문 생성 및 조회 API를 설계한다.
- [ ] 쿠폰과 배송지 조건을 기준으로 서버가 결제 예상 금액을 계산하는 API를 설계한다.
- [ ] 주문 생성 API를 설계한다.
- [ ] 주문 요약 조회 API를 설계한다.
- [ ] 쿠폰 등록, 수정, 삭제 API는 설계하지 않는다.
- [ ] 각 API는 요청, 응답, 성공 상태 코드, 실패 상태 코드, 설계 근거를 포함한다.

- [ ] 시퀀스 다이어그램은 Frontend, Backend, DB를 포함한다.
- [ ] 임시 주문 저장소를 표현하기 위해 Cache 참여자를 추가한다.
- [ ] 클라이언트는 금액 확정 권한을 갖지 않고, 서버가 최종 계산과 검증을 수행한다.
