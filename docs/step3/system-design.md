# 결제하기 버튼 클릭 다이어그램

![alt text](<시퀀스 다이어그램 - 결제하기 버튼 클릭.png>)

결제하기 버튼 클릭 시 발생할 수 있는 두 가지 예외 상황인 결제 금액 오류, 쿠폰 만료와 정상 플로우를 모두 표현하였습니다.

결제 금액 오류의 경우, BE에서 결제 금액과 쿠폰을 검증한 후 400을 반환하면 FE는 사용자를 장바구니 페이지로 리다이렉트합니다. 장바구니로 돌려보내는 이유는, 금액 불일치는 상품 구성 자체가 달라졌을 가능성이 높아 사용자가 처음부터 다시 확인해야 한다고 판단했기 때문입니다.

쿠폰 만료 오류의 경우, 쿠폰 만료 검증 시점을 결제하기 버튼 클릭 시점으로 설정한 이유는 UX를 고려했기 때문입니다. 만약 쿠폰 사용하기 클릭 -> 적용 클릭 두 단계 모두에서 만료 검증을 한다면, 사용자가 이미 만료 알림을 받은 뒤 결제하기를 눌렀을 때 또 다시 만료 알림을 받게 됩니다. 이 경우 사용자 입장에서는 동일한 에러 피드백을 두 번 받게 되므로, 결제 시점에 한 번 더 명시적으로 검증하여 안전망 역할을 하도록 설계하였습니다. 쿠폰 만료 시에는 BE에서 만료된 쿠폰을 DB에서 제거하고 주문을 업데이트한 뒤, FE가 최신 주문 정보를 다시 조회하여 화면을 업데이트합니다.

정상 플로우에서는 결제 완료 후 주문 정보를 한 번 더 조회(GET /orders/:orderId)하여 결제 확인 페이지에 최신 상태를 렌더링합니다. 결제 완료 응답만으로 화면을 구성하지 않고 별도로 조회하는 이유는, 서버 상태를 SSOT로 유지하기 위함입니다.

# 제주도 및 도서 산간 지역 체크박스 클릭 다이어그램

![alt text](<시퀀스 다이어그램 - 제주도 및 도서 산간 지역 체크박스 클릭.png>)

체크박스 클릭 시의 유저 시나리오를 표현하였습니다.

체크박스를 클릭하면 먼저 PATCH /orders/:orderId로 배송지 정보를 서버에 반영합니다. 이후 GET /orders/:orderId로 주문 정보를 다시 조회하고, GET /orders/:orderId/discount로 할인 금액도 재계산합니다.

할인 금액 재계산을 별도로 호출하는 이유는 제주도/도서산간 지역 여부가 배송비에 영향을 주고, 일부 쿠폰(예: 배송비 할인 쿠폰)의 적용 가능 여부나 할인 금액이 달라질 수 있기 때문입니다. PATCH 후 주문 정보를 다시 조회(GET /orders/:orderId)하는 이유도 동일하게 서버 상태를 SSOT로 유지하기 위함으로, FE가 응답 값을 직접 조작하지 않고 서버로부터 항상 최신 상태를 받아 렌더링합니다.

# 주문 확인 클릭 다이어그램

![alt text](<시퀀스 다이어그램 - 주문 확인 클릭.png>)

주문 확인 클릭 시의 유저 시나리오와 주문 만료 스케줄러를 함께 표현하였습니다.

품절 상품 포함 에러의 경우, POST /orders 요청 시 BE에서 상품 재고를 예약하는데, 이때 수량이 0이면 update 실패로 404를 반환합니다. FE는 사용자에게 alert를 띄운 뒤 장바구니를 다시 조회하여 품절 상태를 반영한 화면으로 업데이트합니다.

정상 플로우에서는 주문 생성 후 BE가 가장 할인율이 높은 쿠폰을 자동으로 계산하여 적용합니다. 이후 FE는 주문 확인 페이지로 리다이렉트되면서 GET /orders/:orderId를 호출해 최신 주문 정보를 받아옵니다.

주문 만료 검사는 주문 조회 시점에 수행되며, 만료된 주문이면 404를 반환하고 FE는 장바구니로 리다이렉트합니다.

주문 만료 스케줄러는 FE/USER와 무관하게 BE에서 1분마다 실행되어 만료된 주문의 isExpired를 true로 업데이트하고, 예약된 상품 재고를 취소합니다. 이를 별도 스케줄러로 분리한 이유는, 주문 만료 처리를 특정 사용자 요청에 종속시키지 않고 서버 측에서 독립적으로 보장하며 안전하게 처리하기 위함입니다.

# 쿠폰 사용하기 클릭 다이어그램

![alt text](<시퀀스 다이어그램 - 쿠폰 사용하기 클릭.png>)

쿠폰 사용하기 버튼 클릭 시 쿠폰 선택 모달을 여는 플로우를 표현하였습니다.

버튼 클릭 시 PATCH /orders/:orderId를 먼저 호출하는 이유는, 2+1 쿠폰처럼 주문 상태(hasGift 등)에 영향을 주는 쿠폰이 있을 경우 모달을 열기 전에 서버 상태를 동기화해야 하기 때문입니다. 이후 GET /orders/:orderId로 최신 주문 정보를 받아 모달의 초기 상태를 서버 기준으로 렌더링합니다.

# 쿠폰 적용 클릭

![alt text](<시퀀스 다이어그램 - 쿠폰 적용 클릭.png>)

쿠폰 선택 모달에서 적용 버튼을 클릭했을 때의 플로우를 표현하였습니다.

GET /orders/:orderId/coupons를 호출하여 현재 주문에 적용 가능한 쿠폰 목록과 사용 가능 여부를 BE에서 계산하여 받아옵니다. 이후 GET /orders/:orderId/discount를 추가로 호출하여 현재 선택 상태 기준의 할인 금액을 계산합니다.

두 번의 API 호출로 나눈 이유는 관심사를 분리하기 위함입니다. 쿠폰 사용 가능 여부 계산과 실제 할인 금액 계산은 서로 다른 책임을 가지므로, 하나의 엔드포인트에 모두 담기보다 각각의 역할을 명확히 하였습니다. 모달 렌더링 시 checked 초기값은 주문 조회(GET /orders/:orderId)에서 받아온 coupons 정보를 기반으로 계산합니다.

# 쿠폰 체크박스 클릭

![alt text](<시퀀스 다이어그램 - 쿠폰 체크박스 클릭.png>)

쿠폰 모달 내에서 체크박스를 클릭했을 때의 플로우를 표현하였습니다.

체크박스를 클릭할 때마다 GET /orders/:orderId/discount를 호출하여 현재 선택 상태 기준의 할인 금액을 즉시 재계산합니다. 서버에서 할인 금액을 계산하는 이유는, 쿠폰 조합에 따라 적용 순서나 중복 여부 등 복잡한 비즈니스 로직이 존재할 수 있어 FE에서 직접 계산하지 않고 BE에 위임하는 방식을 선택했기 때문입니다. FE는 응답받은 discountAmount와 현재 사용자 선택 상태를 반영하여 모달 화면을 업데이트합니다.
